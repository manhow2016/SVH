## 1. 结论摘要

1. **V0.3 的主体不是从零建设，而是「确认命名 + 补齐四块」。** 规范 §8 的 `Project` 在本仓库就是 `Content`
   （`type` + `workflowId` + `status` + `metadata`），规范 §35 的「左侧项目流程导航」就是 `CONTENT_SECTIONS`
   （六种内容类型的分区声明，kind 已含 `episode/storyboard/shot/subtitle`）。规范 §4 声称的 Phase 0~6 与仓库实际一致。

2. **真正从零开始的只有四块**：分镜（`storyboard_shots`）、时间线（`timeline_tracks/clips`）、
   导演与动作协议（`director_*` + Action + 确认）、画布/预览（Canvas / Preview）。这四块合计覆盖规范
   §10-13、§25-28、§41 的 11 张表、§43 的 12 条路由。

3. **多处现状比规范更完整，禁止按规范「削减」**：
   - 任务状态：现有含 `waiting_user`（高风险确认闸门的地基），规范 §29 漏了它；
   - 资产类型：现有 14 类，规范 §19 的 10 类是子集（现有多 `brand/costume/music/logo/font`，缺 `subtitle`）；
   - 角色外观：现有 `appearanceSchema` 12 字段，规范 §23 只列 4 个；
   - 四套工作流：现有阶段比规范更细（短剧多出「世界观/分集/角色视觉/场景视觉」，广告多出「字幕」，数字人几乎一一对应）；
   - 错误封装：现状**已经是** §44 的形状（`{error:{code,message,suggestions,retryable}, requestId}`），零裸 500。

4. **规范自己有五处与现状结构性冲突，必须裁决后才能动工**（详见 §5）：§52 的 skill 命名、§41 的分镜/Timeline 存法、
   §7 的 `apps/api/plugins/` 目录、§31 的事件信封维度、§32 的 Provider 抽象维度。

5. **三个「看起来有、实际没接上」的部件**（均已由控制方复核）：
   - **Workflow 执行引擎未接线**：图算法 `computeReadyNodes` / `initRunState` / `isRunFinished` 定义在
     `packages/domain/src/workflow.ts:294,313,355`，全仓**只有 `packages/domain/test/workflow-graph.test.ts` 引用它们**；
     `POST /api/workflows/:id/run` 只创建 pending run 并自带「执行推进属于 Phase 9」的 note。
     四套流程定义很完整，但**没有任何东西按图推进它们**。
   - **Skill 的 `inputSchema`/`outputSchema` 是 JSON Schema 子集而非 Zod**（`packages/domain/src/skill.ts:59-69`），
     且**运行时不校验**：executor 只调 `normalizeInput`（`packages/skills/src/runtime/executor.ts:126-131`），
     两个 schema 目前只用于 API 展示（`apps/api/src/routes/skills.ts:212-213,230-231`）。
     另有一对签名接近 §53 的 `Skill` / `SkillResult`（`skill.ts:159-177`）**全仓无实现、无消费**（死代码）。
   - **全仓没有任何删除能力**：无 delete 工具、无 delete 技能。§12 的 `delete_asset` / `delete_shot`、
     §13 的「删除 / 批量删除需要确认」目前既无从执行、也无需确认。
6. **确认机制的覆盖面比看起来窄**：现有闸门只覆盖「高成本技能」（8 处静态 `risk:'high'` / `requiresConfirmation`
   + 1 处动态 `isHighRisk`）。§13 要求确认的「导出 / 发布」在目录里是 `risk: 'low'`（`packages/skills/src/catalog.ts:382`），
   「覆盖现有版本」「批量删除」无对应标记；也因此**没有**任何「可逆修改 / Undo / Redo」实现（全仓 grep 零命中）。
7. **一处规范未计提的隐形成本**：§67/§68 的 `Preview → Export` 目前没有实现基础 ——
   `edit.video` 只产出 EDL、**不做转码**，全仓没有 FFmpeg 渲染器（`ARCHITECTURE.md` §9 第 6 条）。
   规范把渲染当既有能力，实际它是新工程。同类还有两处"规范当成已有、实际没有"：§50 的**上下文压缩**
   （现状只有按 token 预算裁剪并把裁剪动作记进 notes，无摘要/无「重要决策/待办」保留字段），
   §72 的 **E2E 框架**（无 playwright 配置、无 e2e 目录、根脚本无 e2e）。
8. **文档漂移 2 处**：`ARCHITECTURE.md:199` 原写「共 20 张表」而实际 22（**已修**）；
   `packages/agent/src/context-resolver.ts:102-103` 注释称「加载顺序即优先级（从高到低）」并以 @引用资产为首项，
   而紧随其后的代码实际先加载项目记忆（**未修** —— 两处描述必有一处过时，需与作者确认哪份是意图）。

## 5. 必须裁决的冲突（每条给出选项与后果）

### 5-1 §52 的 skill 命名 vs 现有 43 项目录
- **冲突**：规范给了 16 个 kebab 名（`generate-story`…），现有是 `域.动词` 两层体系（原子能力 + 内容类型编排）。
  6 个规范名在现有目录里**没有对应物**，10 个有对应物但命名不同。
- **A 映射复用**：保留现有 id，新增一份「规范名 → 现有 id」对照表写进文档；6 个缺失的按现有命名风格新增
  （如 `script.rewrite`、`validation.consistency`）。
- **B 按规范重命名**：一次性改名 43 项，涉及 `catalog.ts`、`implementations/*`、Workflow 节点 `skill` 字段、
  种子数据、前端别名（`/by-alias/:alias`）与全部相关测试。
- **C 双轨别名**：保留现有 id，同时把规范名注册为 alias。
- **后果**：B 的成本最高且会动到已落库的 `skills` 表；A 最省但要维护对照表；C 两者兼顾但长期会分叉。
- **建议**：A（或 A+C）。

### 5-2 分镜与 Timeline 存哪
- **冲突**：规范 §41 明说要建 `storyboard_shots` / `timeline_tracks` / `timeline_clips`；
  而现有设计注释写的是「类型特有的深层结构应作为 Workflow 的产出物落在 **ContentState / Canvas** 上」
  （`domain/content.ts:29-31`），但 `ContentState` 与 `Canvas` 全仓**都不存在**（只在资产引用里留了个 `canvas_node`）。
- **A 建表**（按规范）：分镜/时间线成为一等实体，可查询、可排序、可版本化、可被 Timeline UI 直接消费。
- **B JSON 状态**：塞进 `Content.metadata` 或新建 `ContentState`，迁移最轻，但排序/批量/版本/关系查询都要自己做。
- **后果**：A 是后续所有能力（拖拽排序、批量生成、Timeline 轨道、版本对比）的地基；B 到 §26/§28 阶段大概率返工。
- **建议**：A。

### 5-3 §7 的 `apps/api/plugins/` 目录
- **冲突**：规范设想 `plugins/{projects,director,assets,workflows,timeline,versions,tasks}/`；
  现状是 `apps/api/src/routes/*.ts` 11 个扁平文件，`core/app.ts:75` 明确声明「路由插件：一域一文件」。
- **A 沿用 `routes/`**，新域加文件（`shots.ts`、`timeline.ts`、`director.ts`）。
- **B 重构为目录式**：动 11 个文件 + 全部 import + 测试路径。
- **后果**：B 纯属结构搬迁，不产生能力。
- **建议**：A。

### 5-4 §31 的事件信封与事件名
- **冲突**：规范信封含 `projectId`，现有信封是 `sessionId`，且**订阅隔离的安全性建立在会话维度上**
  （`keys.ts:7-10` 明写「以会话为键，跨会话泄漏在结构上不可能发生，而不是依赖查询条件写对」）。
  事件名 14 vs 13，交集只有 `task.progress`。
- **A 保留会话维度，信封**增加**可选 `projectId`**（由服务端从会话反查填充），事件名新增 `director.*` 一族。
- **B 改为项目维度**：重建 Redis Stream 键与订阅过滤，等于重做 Phase 5A 的安全论证。
- **后果**：B 会削弱已有的结构性隔离保证；A 需要加一次「会话 → 项目」的解析（已有 `Session.projectId`）。
- **建议**：A。

### 5-5 §32 的 Provider 抽象维度
- **冲突**：规范要求按媒体类型分接口（`ImageProvider.generateImage` 等）；现状按**协议**分适配器（4 个），
  媒体差异放在 `ProviderDescriptor.config`，注释明确「不把厂商差异硬编码进适配器」。
- **A 沿用现状**：能力已由 `MODEL_CAPABILITIES` 12 类表达（text/script/image/image_edit/video/…），
  5 个已实现技能都跑在这套上。
- **B 引入媒体类型接口层**：在适配器之上再包一层，等于给现有 15 个技能换底座。
- **后果**：B 无收益且回归风险最大。
- **建议**：A。

### 5-7 §53 的 Skill 契约形状与运行时校验
- **冲突**：规范要求单对象 `{inputSchema: ZodSchema, outputSchema: ZodSchema, execute}`；现状是「声明（JSON Schema 子集）
  + 实现（`execute`）」分离，**且运行时不校验输入输出** —— 两个 schema 目前只用于 API 展示。
- **A 保持形状、补上校验**：在 executor 里用 `ajv` 按现有 JSON Schema 校验（`normalizeInput` 之后、输出落库之前）。
  改动面小，收益是「技能返回脏 metadata」在源头被拦住 —— 当前只有 `skill-execution.test.ts` 在测试期检查。
- **B 改为 Zod**：要重写 43 项目录的 schema，并牵动 API 展示与前端表单契约（`asset-form-contract.test.ts` 那类机械护栏）。
- **C 维持现状**：等于承认 schema 只是文档。
- **后果**：B 的收益与 §53 字面一致但回归面最大；A 用最小代价补上真实缺口。
- **建议**：A（顺带处理 `skill.ts:159-177` 那对无消费的 `Skill`/`SkillResult` 死代码：删除或注明用途）。
