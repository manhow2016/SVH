## 1. 背景与目标

V0.3-1 交付了分镜、时间线、导演动作三组实体的**领域契约与仓储**，但全仓**没有任何一条路由能碰它们**：
`apps/api/src/routes/` 下只有 assets / contents / projects / tasks / agent / skills / workflows /
events / files / providers / health 十一组。也就是说「一个内容有 12 个有序镜头」这件事在数据库里成立，
在 HTTP 上不成立。

本片把这条竖切补到 API 与事件两层：**用 HTTP 请求完成镜头编排、片段编排、动作提案与确认，
并让变化以事件的形式落到既有会话流上。**

目标一句话：**让「前端不 import 仓储、只打 HTTP 也能把一条内容编排到可拍状态，
并且 AI 的每项修改都以提案形态进入可确认闭环」这件事成立并被真库集成测试锁住。**

本片**不交付**：动作执行（V0.3-5）、UI（V0.3-6）、版本（V0.3-5）、workflow 推进（既有 workflow
面自成一摊，本片不动）、以及任何鉴权（仓库现状是全仓无鉴权层，本片不发明按用户隔离的语义）。

## 3. 路由面（16 条）

三条既有约定全部沿用，**不新造第二套**：

- 请求校验走 `apps/api/src/core/validate.ts` 的 `parseBody` / `parseQuery` / `parseIdParam`，
  校验失败抛 `ValidationError` → 全局处理器转 400 + `issues`；
- schema **复用 V0.3-1 已交付的领域契约**（`createShotSchema` / `updateShotSchema` /
  `reorderShotsSchema` / `createClipSchema` / `updateClipSchema` / `moveClipSchema`），
  不新增同义 schema；路径已提供的归属字段用 `.omit()` 从请求面剔除（§3.1 第 2 点）。
  唯一的例外是 `POST …/director/actions` 的那层薄信封（§3.3 第 5 点）—— 它不重复任何校验；
- 路由文件按域拆分并注册进 `core/app.ts`，**沿用既有的两条惯例**（读码核实）：
  ① 每个插件用 `{ prefix: '/api/<根>' }` 注册，插件体内路径写成相对（`app.get('/:id')`）；
  ② **父资源作用域的子路由归父文件** —— `GET /api/projects/:id/assets` 写在 `projects.ts:173`、
  `GET /api/contents/:id/assets` 写在 `contents.ts:228`、`GET /api/projects/:id/contents`
  写在 `projects.ts:130`，都没有反向 import 子域文件。
  于是本片 16 条的落点是**混排**的，这是遵循惯例的结果，不是随意：

  | 文件 | 承载的路由 | 条数 |
  | --- | --- | --- |
  | `contents.ts`（prefix `/api/contents`） | `GET/POST /:id/shots`、`POST /:id/shots/reorder`、`GET /:id/timeline`、`POST /:id/timeline/track-defaults` | 5 |
  | `projects.ts`（prefix `/api/projects`） | `GET/POST /:id/director/actions` | 2 |
  | `shots.ts`（新增，prefix `/api/shots`） | `PATCH /:id`、`DELETE /:id` | 2 |
  | `timeline.ts`（新增，prefix `/api/timeline`） | `POST /tracks/:id/clips`、`PATCH /clips/:id`、`POST /clips/:id/move`、`DELETE /clips/:id` | 4 |
  | `director.ts`（新增，prefix `/api/director`） | `POST /actions/:id/confirm`、`/reject`、`/cancel` | 3 |

  合计 5 + 2 + 2 + 4 + 3 = **16**，与 §3.1-§3.3 三张表的条数一致（三张表按域分列，
  本表按文件归集，两处口径必须对得上 —— 数不上就是漏了一条或多写了一条）。

所有**写**路由都接受一个可选的 `sessionId`，但它在两类入口上的地位**不同**，不要混为一谈：

- `POST /api/projects/:id/director/actions`：它是**业务字段**，从 body 取，随动作落库
  （`DirectorAction.sessionId`），之后 confirm / reject / cancel 的投递目标就是从这一列读出来的；
- shots 与 timeline 的全部写路由：它**只是投递目标**，从 query 取（`?sessionId=`），
  不落库、不参与写入语义（镜头与片段挂在内容下，没有承载它的列；为它加列属于推倒 V0.3-1
  的数据模型）。为什么不用 body：见 §3.1 第 2 点的实测 —— 三个更新类契约带 `.refine()`，
  是 `ZodEffects`，不接受 `.extend()`，为了塞一个非业务字段去重写契约是本末倒置。

两种情形下不带 `sessionId` 一律「写成功、不发事件」。细节见 §4.2。

### 3.1 分镜（5 条：`contents.ts` 3 + 新增 `shots.ts` 2）

| 方法与路径 | 仓储入口 | 响应 | 事件 |
| --- | --- | --- | --- |
| `GET /api/contents/:id/shots` | `listShots(contentId)` | `{ shots: StoryboardShot[] }` | — |
| `POST /api/contents/:id/shots` | `createShot({contentId, ...body})` | 201 + 单镜头 | `shot.changed` |
| `PATCH /api/shots/:id` | `updateShot(id, patch)` | 200 + 单镜头 | `shot.changed` |
| `DELETE /api/shots/:id` | `deleteShot(id)` | 204 | `shot.changed` |
| `POST /api/contents/:id/shots/reorder` | `reorderShots({contentId, orderedShotIds})` | 200 + `{ shots }`（全量，与 GET 同形状） | `shot.changed` |

两个必须写清的语义点：

1. **列表不分页。** `paginate()` 只用于 §43 里的集合分页面；镜头的 `index` 是
   「内容内自 0 连续」的编排语义（reorder 依赖全量顺序），分页会把它切成碎片。
   响应是裸数组信封 `{ shots }`，与 `GET /api/contents/:id/timeline` 的形态一致。
   超过 `INDEX_OFFSET`（10 万）的保护在仓储里（`assertIndexOffsetSufficient`），
   本片不为它编造 HTTP 层语义，见 §9 风险 4。
2. **归属字段一律由路径提供，body 里不允许出现。** V0.3-1 的仓储入参 schema 是
   **扁平的**（`createShotSchema` 有必填 `contentId`、`createClipSchema` 有必填 `trackId`、
   `reorderShotsSchema` 有必填 `contentId`）—— 那是仓储层的正确形状，路由不能反过来改它。
   机制上分两种写法（**都在 `packages/domain` 内实测过**，zod 3.25.76）：

   - **创建 / 重排类**（`createShotSchema`、`createClipSchema`、`reorderShotsSchema`，
     都是纯 `.strict()` 的 ZodObject）：请求面用 `契约.omit({ 路径字段: true })`，
     再把路径参数注入后交给仓储。实测 `.strict()` 经 `.omit()` **仍然生效**，
     所以 body 里再带 `contentId` / `trackId` 会得到 400 + `unrecognized_keys`，
     不需要新写任何 schema。
     为什么不用「解析整份 body 然后覆盖同名字段」：那会让客户端传的 `contentId` 被
     **静默忽略**，出现「路径说 A、body 说 B」却返回 201 的形态。
   - **更新 / 移动类**（`updateShotSchema`、`updateClipSchema`、`moveClipSchema`）：
     **原样直接用**。它们都带 `.refine()`，实测结果是 `.refine()` 之后是 `ZodEffects`，
     `omit` 与 `extend` **两个方法都不存在**（`typeof updateShotSchema.omit === 'undefined'`（探针；直接调 `.extend()` 报 `is not a function`））——
     想改造它只能重新包装一层，而它们本来就不含归属字段，没有要剔除的东西，正好不必动。

   这条区分也是 `sessionId` 走 query 而不是 body 的原因（见 §3 前言）：
   要给带 refine 的契约加一个非业务字段，就得为它另写一层 schema —— 那才是真的重复模型。

### 3.2 时间线（6 条：`contents.ts` 2 + 新增 `timeline.ts` 4）

| 方法与路径 | 仓储入口 | 响应 | 事件 |
| --- | --- | --- | --- |
| `GET /api/contents/:id/timeline` | `getTimeline(contentId)` | 200 + `Timeline`（轨道含片段） | — |
| `POST /api/contents/:id/timeline/track-defaults` | `ensureDefaultTracks(contentId)` | 200 + 轨道数组 | `clip.changed` |
| `POST /api/timeline/tracks/:id/clips` | `createClip({trackId: 路径参数, ...body})` | 201 + 单片段 | `clip.changed` |
| `PATCH /api/timeline/clips/:id` | `updateClip(id, patch)` | 200 + 单片段 | `clip.changed` |
| `POST /api/timeline/clips/:id/move` | `moveClip(id, target)` | 200 + 单片段 | `clip.changed` |
| `DELETE /api/timeline/clips/:id` | `deleteClip(id)` | 204 | `clip.changed` |

- `GET timeline` 对**尚无轨道的内容**返回 `tracks: []`，**不 404、也不在 GET 里偷偷补轨**
  （读码核实：`getTimeline` 只 `findMany` 后 `timelineSchema.parse`，
  而 `timelineSchema.tracks` 是无最小长度的数组，空树合法）。补齐是显式的 `track-defaults`，
  所以「先补轨、后建片段」是客户端必须走的顺序 —— 这条写进 §8.4 的验收链。
- `track-defaults` 是幂等补齐（`ensureDefaultTracks` 按 kind 去重），返回 200 而不是 201：
  它可能一条都没新建。默认三轨是 video / audio / subtitle（timeline.ts:88-92）。
- **未知 `trackId` 建片段目前是 500**（读码核实：`createClip` 不校验轨道存在，
  `assertTrackFree` 查不到同行视为「没有重叠」，直接落到 `create` → FK 违反 P2003 → 500）。
  与前置 6 同批修，目标 404 + `TIMELINE_CLIP_NOT_FOUND`（`context` 里带 `trackId`，见 §7 末）。

### 3.3 导演动作（5 条：`projects.ts` 2 + 新增 `director.ts` 3）

| 方法与路径 | 仓储入口 | 响应 | 事件 |
| --- | --- | --- | --- |
| `GET /api/projects/:id/director/actions` | `listActions(projectId, {status?})` | 200 + `{ actions: DirectorAction[] }` | — |
| `POST /api/projects/:id/director/actions` | `createAction({...})` | 201 + 单动作 | `director.action.changed` |
| `POST /api/director/actions/:id/confirm` | `confirmAction(id)` | 200 + 单动作 | `director.action.changed` |
| `POST /api/director/actions/:id/reject` | `rejectAction(id, reason?)` | 200 + 单动作 | `director.action.changed` |
| `POST /api/director/actions/:id/cancel` | `cancelAction(id, reason?)` | 200 + 单动作 | `director.action.changed` |

五个必须写清的语义点：

1. **`actor` 由路由硬编码为 `'user'`，不在 body 里。** HTTP POST 到提案面就是用户行为；
   `actor: 'agent'` 的提案由 V0.3-3 的 Agent 工具层**直接调仓储**产生。若把 `actor` 开放给 body，
   外部可以随意伪造「这条是 AI 提的」，而它同时是审计与 UI 归因的依据。
   `CreateActionInput.actor` 保留两值不变（仓储层语义正确），只是这条入口不暴露。
2. **`requiresConfirmation` 与 `status` 都不可由调用方指定**：`createAction` 的入参里本就没有
   （由 `requiresConfirmation()` 从动作类型、目标数量、`changes.overwrite` 推导 —— 仓储层
   「多传同名字段也读不到」这层语义已由 V0.3-1 的测试锁住）。
   **HTTP 面比仓储面更严**：请求 schema 是 `.strict()` 的，所以从路由传这两个键会得到 400
   `unrecognized_keys`，而不是「收下但忽略」。两层都要有断言，因为它们是**不同的行为**：
   仓储按字段取用、不校验未知键（`CreateActionInput` 里根本没有这些字段），
   路由对外部输入不留歧义。
3. **不自动批准落 `approved` 的动作是本片的已知终点态。** 决策 ② 不做执行，所以
   无需确认的动作会以 `approved` 停在库里。**这不是缺陷**：V0.3-5 的执行层起点正是
   「捞 `status = approved` 的行去执行」，本片交付的就是那张队列的正确性。
4. **状态转移失败目前是 500，本片必须变成可断言的 4xx**（读码结论，与本文初稿相反）：
   `resolveCasMiss`（director-actions.ts:243-272）三条判定分支**全部抛裸 `Error`**，
   而行不存在的分支根本走不到判定 —— `transition()` 在 CAS 未命中后用
   `findUniqueOrThrow` 读当前状态（:290），未知 id 直接抛 Prisma P2025 → 500。
   四种真实语义必须分开，因为客户端要做的事完全不同：

   | 情形 | 仓储现状 | 本片目标 |
   | --- | --- | --- |
   | 行不存在 | P2025 → 500 | 404 + `DIRECTOR_ACTION_NOT_FOUND` |
   | 已在目标状态（重复提交） | **返回既有行**（幂等，不覆盖 `confirmedAt`） | 保持 200 —— 这是既有正确语义，不是缺陷 |
   | 领域状态机不允许该转移 | 裸 `Error` → 500 | 409 + `DIRECTOR_ACTION_STATE_CONFLICT` |
   | 状态机允许、但本入口不接受该来源 | 裸 `Error` → 500 | 409 + 同上，`retryable: true`（被并发抢先时靠它自愈） |

   「重复 confirm 得到 200 幂等」这条本文初稿写成了 409，是错的：`resolveCasMiss` 的第一分支
   `currentStatus === spec.to`（:250）明确返回既有行，且注释说明这是刻意不覆盖 `confirmedAt` / `result`。
   要触发 409，得用**转移方向非法**的组合（如 `confirm` 之后再 `reject`：
   `rejectAction` 只接受 `awaiting_confirmation`，而 `approved → rejected` 领域里不允许，
   命中 `assertDirectorActionTransition`（:255）那条分支）。验收链 §8.4 已按此改写。
5. **`POST` 的请求 schema 需要新建一个，但它是「信封」不是「重做校验」。**
   `CreateActionInput` 的 `payload` 是 `unknown` —— 动作结构由仓储里的
   `parseActionPayload(type, payload)` 把关（§9 风险 5 已核实这条路是 400）。
   路由侧只加一层薄信封 schema：`z.object({ type, payload: z.unknown(), contentId?, sessionId? }).strict()`，
   `projectId` 取路径、`actor` 固定 `'user'`（第 1 点）。
   **刻意不在这里 parse `payload`**：那是 `DIRECTOR_ACTION_SCHEMAS` 的职责，
   两处各校验一份必然漂移（同一逻辑，`parseActionPayload` 的注释也是这么说的）。

## 4. 事件面

### 4.1 新增三个事件类型（`packages/domain/src/transport.ts`）

`SSE_EVENT_TYPES` 现在 13 个。本片加 3 个，成为 16：

| 类型 | data 载荷 | 发布者 |
| --- | --- | --- |
| `shot.changed` | `{ contentId, shotId: string \| null, action: 'created' \| 'updated' \| 'deleted' \| 'reordered' }` | shots 路由 |
| `clip.changed` | `{ contentId, clipId: string \| null, action: 'created' \| 'updated' \| 'moved' \| 'deleted' \| 'tracks_ensured' }` | timeline 路由 |
| `director.action.changed` | `{ actionId, type, status, contentId: string \| null }` | director 路由 |

**`data` 里不放 `sessionId`，也不放 `projectId`。** 前者由流 key 与信封承担
（`StreamedEvent.sessionId` 以订阅方声明的会话为准，见 `packages/realtime/src/parse.ts`），
后者由信封的 `projectId` 承担（§5）。同一条信息出现在信封与载荷两处，是本项目反复踩过的
「两处一写就必然漂移」的形态。

三条共同约束：

- **`data` 只带标识与状态，绝不带整行。** 客户端收到变更信号后自行拉取（既有 `asset.changed`
  就是这个形态），否则事件流变成一份份快照的堆积，`MAXLEN` 上限会很快把有用的事件挤掉。
- **`shotId` / `clipId` 什么时候为 `null`？** 删除**不**为 null：删掉之后行虽然没了，
  但客户端仍然需要知道**是哪一条**没了才能精确失效本地缓存，`action` 字段区分死活。
  为 null 的只有一种情形 —— **一次影响多行、没有单一主体**（`reordered` 整批重排、
  `tracks_ensured` 补齐轨道）。这两种情况下客户端的正确反应本来就是「重新拉全量」，
  所以 `null` 的语义是「去拉列表」，不是「不知道是谁」。**不保留已删除行的完整载荷**：
  事件只说「哪条没了」，不缓存"它生前长什么样"，那需要额外存储，而消费方不需要。
- **`director.action.changed` 只发一条类型**（决策 ⑤）。转移种类放 `data.status`，
  于是「客户端要处理几种动作事件」恒为 1，新增一种状态转移不用改 `SSE_EVENT_TYPES`。
  `packages/realtime/src/parse.ts` 也**不需要**跟着改：它的判据是从 domain 派生的
  `EVENT_TYPE_SET = new Set(SSE_EVENT_TYPES)`（parse.ts:15），加类型即自动认得 ——
  本片只补一条「枚举与 parse 不漂移」的断言（§8.2），不去改代码。

### 4.2 投递到哪条会话（本文口述设计里没有这一层）

会话流是**按 session 切的**，所以每条事件都必须有一个 `sessionId`。三类各自的来源不同，
逐条钉死，否则实施时只能靠猜：

| 事件 | `sessionId` 来源 | 依据 |
| --- | --- | --- |
| `director.action.changed`（confirm / reject / cancel） | **动作行里存的 `sessionId`**（读库得到，客户端无法指派） | `DirectorAction.sessionId` 可空；提案由谁在哪条会话里发起，行本身就是事实 |
| `director.action.changed`（create） | body 的可选 `sessionId`；**不带就不发** | 沿用既有做法：`agentChatRequestSchema.sessionId`（session.ts:207）、`POST /api/tasks` 的 `sessionId`（task.ts:73）都是客户端声明投递会话 |
| `shot.changed` / `clip.changed` | query 的可选 `sessionId`（`?sessionId=`），带才发 | 镜头与片段挂在**内容**下、不在会话下，URL 里给不出会话；不用 body 的理由见 §3 前言 |

- **不带 `sessionId` 就不发，且这不是错误**：`publishSessionEvent` 对空 sessionId 直接返回 `null`
  是既有契约（events.ts:69），本片一字不改。用户在项目页手工编排、没有会话在场时，
  本来也没有任何订阅者需要这条回声。
- **为什么不按 `Session.contentId` 反查「这条内容的所有活跃会话」再扇出**：那样每次写都要多一次
  查询，且同一次编排会往 N 条会话各发一份（`seq` 语义没坏，但事件量按会话数放大）。
  登记为 V0.3-6 需要「多标签页同步」时的升级路径 —— 反查可行（`agent-deps.ts:338-345` 确实会写
  `Session.contentId`），只是本片没有这个需求。
- **安全形状不变**：客户端只能往它**已经知道 id** 的会话里发。这与既有 `task.status` /
  `asset.changed` 完全同源，本片不新增也不削弱隔离模型（`packages/realtime/src/keys.ts` 的论证照旧成立）。

### 4.3 发布时机

- **只在仓储写成功之后发**（不是写完就发、也不是发完再写）。路由里 `await` 仓储、再 `await`
  `publishSessionEvent(...)`；发布器契约上不抛，所以发布失败不会把已成功的写请求变成 500。
- 三个类型的发布点全部在 API 层，因此本片**不动 worker**。worker 何时开始发这些事件，
  属 V0.3-3（Agent 工具层）与 V0.3-5（执行层）的范围。

## 5. 信封 `projectId`：注入点读侧（设计期修正）

5-4 A 案要解决的问题：事件流按会话切，而分镜与片段挂在**内容**下、内容挂在**项目**下，
动作直接挂在项目下；客户端（V0.3-6 的项目级 UI）拿到一条 `director.action.changed`，
需要知道它属于哪个项目，而这个信息**不能由客户端自报**
（会话流 key 本身就是隔离边界，`packages/realtime/src/keys.ts` 的论证成立的前提是
「客户端只能订阅自己知道的会话」）。

方案：`SseEnvelope` 加可选 `projectId?: string`，服务端从 `Session.projectId` 反查填充。
`Session.projectId` 可空，所以字段可选是语义正确，不是兜底妥协。

**落点在读侧，不在发布侧。** 读码后确认发布侧有三条硬约束：

1. **发布路径有两条**：`apps/api/src/core/events.ts` 的 `publishSessionEvent`（API 侧）与
   `apps/worker/src/events.ts` 的 `createEventSink`（worker 侧）。在发布侧填 = 两处各写一份反查逻辑，
   违反「不重复实现已有能力」。
2. **worker 侧的 `emit` 是刻意同步的**（注释原文：任务的执行路径绝不能因为 Redis 抖动而变慢或失败）。
   发布侧填 `projectId` 就要在任务执行路径上插一次数据库读，直接违反这条既有契约。
3. **读侧本来就在查 session**：SSE 端点 `GET /api/agent/sessions/:id/events`
   （`eventRoutes` 以 prefix `/api/agent` 注册，app.ts:88 —— 完整路径带这段前缀）
   的处理体里就有 `prisma.session.findUnique({ where: { id: sessionId }, select: { id: true } })`。
   把 select 扩成 `{ id: true, projectId: true }`，**新增查询数为 0**。

而读侧落点还顺带覆盖了 replay：`session.ready` 帧、心跳 `ping`、补发区间与实时区间
**全部经过同一个 `frame(envelope, streamId?)` 函数**，注入一次即四类帧都带。

具体做法：

- `packages/domain/src/transport.ts`：`SseEnvelope` 加 `projectId?: string`，
  `sseEnvelopeSchema` 同步加 `projectId: z.string().min(1).max(64).optional()`（schema 与 interface 同源）。
- `packages/realtime/src/parse.ts`：**不改**。它产出的是 `StreamedEvent`（流内记录），不是信封；
  信封由 SSE 路由组装。这条结论连同「信封上的 `projectId` 是投递时解析的归属」一起写进
  `docs/ARCHITECTURE.md` §6.9 的「事件类型与来源」小节（那张表列的就是发布点，本片加三行）。
- `apps/api/src/routes/events.ts`：`select` 加 `projectId`；`frame()` 的**三个调用点**都传 projectId。
  实现上给 `frame()` 加一个 `projectId?: string` 形参（而不是在调用点手工展开对象），
  这样「漏传」在类型上就可见。
- Redis 流内记录**不带** `projectId`。语义是「投递时解析归属」，不是「事件自带归属」。
  这条要写进注释，否则后来者会误以为流里少写了一个字段从而去补，两处一写就必然漂移。

## 7. 错误契约

`ERROR_CODES`（errors.ts:15）现在没有 shot / timeline / director 类码。补 4 个，沿用 `ASSET_NOT_FOUND` 的命名法：

| code | HTTP | 触发 |
| --- | --- | --- |
| `SHOT_NOT_FOUND` | 404 | 未知镜头 id |
| `TIMELINE_CLIP_NOT_FOUND` | 404 | 未知片段 id / 未知轨道 id |
| `DIRECTOR_ACTION_NOT_FOUND` | 404 | 未知动作 id |
| `DIRECTOR_ACTION_STATE_CONFLICT` | 409 | 状态机前置集不满足，或被并发抢先 |

**加一个码会强制改四处**（这是既有设计，本片只是走它）：`ERROR_CODES` 枚举 →
`HTTP_STATUS_BY_CODE`（`satisfies Record<ErrorCode, number>`，漏一项**编译失败**）→
`USER_MESSAGE_BY_CODE`（同样 `satisfies`，漏一项编译失败）→
`SUGGESTIONS_BY_CODE`（`Partial`，可选，但 404 / 409 都该给）。

**载体类**：`NotFoundError` 与 `ConflictError` 把 code 写死成 `NOT_FOUND` / `CONFLICT`
（errors.ts:311、:331），所以专属 code 必须走既有惯例 —— 一个域一个小类，
形状照 `AssetError`（`Extract<ErrorCode, ...>` 联合）：

- `ShotError('SHOT_NOT_FOUND', ...)`
- `TimelineError('TIMELINE_CLIP_NOT_FOUND', ...)`
- `DirectorActionError('DIRECTOR_ACTION_NOT_FOUND' | 'DIRECTOR_ACTION_STATE_CONFLICT', ...)`

其余复用既有码，**不新增同义码**：`ValidationError` → 400（含 `issues`），
`CONFLICT` → 409（片段重叠这类业务冲突），`ASSET_IN_USE` → 409（前置 2 的删除守卫）。

轨道 id 未知与片段 id 未知共用 `TIMELINE_CLIP_NOT_FOUND` 还是分开？
分开会多一个码且 `TIMELINE_TRACK_NOT_FOUND` 只在一条路由上可能触发 —— 本片共用一个码，
靠 `suggestions` 与 `context` 区分，登记为可回退项（实施中若发现客户端无法区分再拆）。

## 8. 测试与验收

### 8.1 路由集成测试（真库 + `app.inject()`）

沿用 `apps/api/test/api-contract.test.ts` 的既有形态：`buildApp()` + 真库 + 结束前 `disconnectPrisma()`
并清掉测试夹具。**不用 mock 仓储** —— 本片要验的正是「路由 → 仓储 → 数据库」这条链是否成立。

- 16 条路由**每条至少一个 happy path + 一个 4xx**；
- 4xx 覆盖面按类型算，不按条数凑：非法 id（400 + `issues`）、未知 id（404 + 专属 code）、
  状态机冲突（409 + `DIRECTOR_ACTION_STATE_CONFLICT`）、空 patch（400）；
- 每个断言都验 `requestId` 存在（§44 契约的最低要求）。

### 8.2 事件契约测试

从**SSE 线上**读，不从 Redis 读（信封是读侧组装的，只读 Redis 会验到一个不存在的东西）：

- 建会话 → 打路由（带 `sessionId`）→ 订阅流，断 `shot.changed` / `clip.changed` /
  `director.action.changed` 各至少一条；
- 断信封带服务端反查出的 `projectId`；并且**在请求里塞同名字段无法影响它**
  （`projectId` 不在任何请求 schema 里，塞进去会被 `.strict()` 拒成 400 —— 这条要断言的是"拒"，
  不是"忽略"）；
- 断 `data` 只有标识与状态，**没有整行**（对 `data` 的键集合做**精确**断言，不是 `toMatchObject`），
  且 `data` 里**不含** `sessionId` / `projectId`（§4.1 的去重约定）；
- 断 confirm 的投递目标**只来自行内 `sessionId`**：对一个行内 `sessionId` 为空的动作，
  在 confirm 请求上带一个有效 `?sessionId=` 也**不得**产生事件（负控制：给动作补上会话后事件出现）。
  这条断言的是「**转移类**入口不接受客户端指派目标」，与 create 侧**刻意不同** ——
  create 是用户自己发起提案，投递目标由他声明（与 `POST /api/tasks` 带 `sessionId` 同构）；
  confirm / reject / cancel 是对**既有提案**的响应，目标由行内事实决定，否则任何人都能
  往别人的会话流里推别人的动作状态。
- 断不带 `sessionId` 的写请求**成功返回 200/201 但不产生事件**（这是 §4.2 的「带才发」，
  也是本片最容易测不出来的一条 —— 若把「不发」实现成「发空会话」，SSE 侧会直接报错）；
- 断 `type` 必须能被 `parseStreamEntry` 认得（`SSE_EVENT_TYPES` 与 parse 不漂移）；
- 断**流内记录不含 `projectId` 字段**（读码核实：`publish` 的 XADD 只写 `type` / `at` /
  `sessionId` / `seq` / `data` 五个字段，publisher.ts:86-103），而 replay 帧仍带出
  正确的 `projectId` —— 这是 §5 读侧落点的可测后果，也是「投递时解析归属」与「事件自带归属」
  两种设计的分辨点。

### 8.4 验收链（把 V0.3-1 spec §7.2 的仓储链升级为 HTTP 链）

一条集成用例跑完整个链条（下文的「带 sessionId」：shots / timeline 走 query `?sessionId=`，
director create 走 body —— 见 §3 前言）：

```text
建项目 + 内容 + 会话
→ POST shots × 12（带 sessionId）→ GET 断 index 0..11
→ POST shots/reorder（逆序，带 sessionId）→ GET 断 index 仍是 0..11 且顺序反转
→ GET timeline 断 tracks 为空数组（读侧不自动补轨）
→ POST timeline/track-defaults（带 sessionId）→ 断三条默认轨；再打一次 → 断幂等（仍三条、order 不变）
→ POST clips（video / audio / subtitle 各若干，含相邻不重叠的边界）
→ POST clips/:id/move（改轨 + 改起点）
→ 断 GET timeline 的重叠守卫与不重叠事实同时成立
→ 断跨内容引用被拒（用另一内容的轨道 + 本内容的镜头，前置 9）
→ POST director/actions（update_shot 提案，带 sessionId）→ 断 requiresConfirmation 由服务端推导
→ 断 body 里塞 requiresConfirmation / status / actor → 400 + unrecognized_keys（请求 schema 是 strict）
→ POST actions/:id/confirm → 200 + status=approved
→ 再 POST confirm → **200 幂等**（返回既有行，confirmedAt 不被覆盖）
→ POST actions/:id/reject → 409 + DIRECTOR_ACTION_STATE_CONFLICT（approved→rejected 非法）
→ 另造两条动作，分别走 /reject（从 awaiting_confirmation）与 /cancel（从 approved）→ 200
→ 未知动作 id 的 confirm → 404 + DIRECTOR_ACTION_NOT_FOUND
→ 全程 SSE 侧断事件按 seq 单调、type 与 status 正确、信封带 projectId、data 不带整行
→ 同一链条再跑一遍**全部不带 sessionId** 的写：断响应码完全相同、但流上一条事件都没有
```

### 8.5 门禁

`pnpm turbo run lint typecheck test build --force` 全绿才算完成。**测试数不预先承诺**
（上一片靠这条避免了计数漂移）；跑完把实测数回写实施计划。

## 9. 风险与注意事项

1. **无鉴权是仓库现状，不是本片引入**。16 条路由沿用既有 `core/app.ts`（无 auth 层）。
   本片**不发明**按用户 / 按项目的隔离语义 —— 那需要先在 `Session` 之外建立主体概念，
   超出 V0.3-2 范围。
2. **`projectId` 只覆盖经 SSE 投递的事件。** 直连 Redis 流的其他消费者（若有）看不到该字段。
   这是读侧落点的直接后果，写进 `routes/events.ts` 注释与 `ARCHITECTURE.md` §6.9。
3. **`shot.changed` / `clip.changed` 与 `content.changed` 语义重叠。** 后者是已注册但**无发布者**的类型。
   本片不启用它（启用即引入第四种「我该监听哪个」的歧义），登记为 V0.3-6 要一并裁定的问题；
   若届时决定删掉这两个新类型改用 `content.changed`，回退成本是枚举 1 处 + 9 个发布点的类型名
   （shots 4 处、timeline 5 处；director 的 4 处不受影响）。
4. **`INDEX_OFFSET` 守卫抛裸 `Error`** → 500 + 技术报文。真库造不出 10 万镜头，
   本片不处理，登记为已知限制。
5. **`createAction` 的 payload 校验已经是 400，本片不重做。** 读码核实（本文初稿把它写成待确认）：
   未注册动作类型走 `parseActionPayload`（director.ts:201-219，未注册分支在 :205-211）
   抛 `ValidationError` 并带 `issues`；
   类型已注册但结构非法走 `DIRECTOR_ACTION_SCHEMAS[type].parse(payload)`，抛裸 `ZodError`，
   而 `toSvhError`（errors.ts:483-488）**已经**把 `ZodError` 映射成 `ValidationError` → 400。
   所以这条只需要一个集成断言把「400 而不是 500」钉住，**不需要新增归一化代码**；
   路由层也不重复这份校验。
6. **枚举与计数的漂移面**（逐处核过，`grep -rn "SSE_EVENT_TYPES\|KNOWN_EVENT_TYPES" apps packages docs`）：
   ① `packages/realtime/src/parse.ts` **不用改也不该改** —— 它的判据是派生的
   `EVENT_TYPE_SET = new Set(SSE_EVENT_TYPES)`（:15），加类型即自动认得（§4.1）；
   ② `apps/web/src/features/agent/agentEvents.ts` 的 `KNOWN_EVENT_TYPES` 是**手写的第二份 13 项**，
   文件头注释写明这是刻意的（前端不引 `@svh/domain`，落后的表现是「未知事件只记一条 warn」，
   不崩整条流）。**本片不改它**：V0.3-2 没有任何界面消费这三个类型，改了反而制造「界面已支持」的假象。
   登记给 V0.3-6（那一片要渲染它们）；
   ③ `docs/ARCHITECTURE.md` §6.9 的原话是「事件类型只在 `packages/domain/src/transport.ts` 的
   `SSE_EVENT_TYPES` 定义一次」（:548），§3.1 讲的是 Prisma 枚举与 domain 枚举的漂移测试 ——
   两处都不覆盖 ② 那份手写清单。本片在 §6.9 的小节里补一句指向它，
   免得后来者把「定义一次」读成「全仓只有一份字面量」、顺手把 ② 当成重复实现删掉；
   ④ 全仓所有写「13 个 / 十三种」的注释（`transport.ts` 的枚举上方、`ARCHITECTURE.md`）。
   这一条的方法论来自 `docs/ARCHITECTURE.md` §10.2：绝对化措辞与计数必须逐处核。
7. **跨项目引用不校验（登记为已知限制）**。前置 9 只管「轨道 / 片段 / 镜头同内容」；
   `shot.imageAssetId`、`clip.assetId` 仍可以指向**别的项目的资产**。修它要给每条写入路径补
   项目归属比对，而仓库现在没有主体概念（风险 1）—— 在无鉴权的单用户库里这属于语义洁癖
   而非可被利用的越权，这笔账应由鉴权那一片统一付。
